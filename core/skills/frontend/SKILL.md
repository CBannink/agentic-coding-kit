# Frontend design

Identify the audience, page purpose and primary action. Inspect existing screens, tokens, components and relevant design notes. Existing brand rules and explicit user direction outrank generic aesthetic advice. Distinguish a marketing page from a dense application screen; a settings form does not need a landing-page hero.

## A small visual decision
For new design, state hierarchy, layout, type/color roles and a justified distinguishing detail. Keep this inline unless workers need a shared decision. Reuse existing tokens. With no established system, choose a small coherent palette from the product's subject, with readable text and visible interaction states. Neutral surfaces and an intentional accent are a starting option, not a compulsory theme.

Avoid unrequested purple/blue gradients, neon-on-black dashboards, frosted cards, gradient headlines, decorative blobs and repeated feature-card grids as defaults. Do not replace one template with an obligatory cream/serif template. A color, font or rounded corner alone is not evidence of poor design; preserve a deliberate existing brand, including purple or a system font. Remove decoration that competes with the task, not necessary information density.

Use the project's actual component and icon system. Do not invent ad-hoc inline SVG icons, use emoji as interface controls, or mix icon families without a reason. Verified library SVG components and existing approved SVG assets are allowed; meaningful charts/diagrams are not banned. Confirm real exported icon names, consistent visual weight and accessible labels; do not fabricate a logo. No new icon dependency without authorization.

## Build and verify
Use specific, truthful content. Do not invent testimonials, customer logos, metrics or unsupported product claims to fill a template. Provide relevant loading, empty, error, disabled and success states. Keep controls semantic; check labels, keyboard navigation, visible focus, contrast, touch usability, zoom and long text. Motion should explain state and respect reduced-motion preferences, not decorate every element.

Inspect the rendered candidate at relevant narrow/wide layouts and exercise the primary interaction using an available approved tool. Capture evidence without a mandatory polish cycle. A build or screenshot alone does not prove accessibility or interaction correctness. When a browser, assistive test or asset is unavailable, report the gap explicitly. Return the decisions, reused components/assets and actual evidence in the existing handoff; do not create another reviewer or rewrite the site's theme outside scope.
