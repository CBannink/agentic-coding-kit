## Default Agent Matrix

### Surface Reviewers

- `software-reviewer`
  Purpose: logic, regressions, edge cases, architecture fit, and missing tests.
  **INLINE/TARGETED**: also covers test-quality inline — ask: is new behaviour tested? Do test names describe behaviour? Are mocks accurate? Are error/edge cases covered?
- `security-reviewer`
  Purpose: auth, trust boundaries, injection, leakage, abuse cases, and sensitive flows.
  **Trigger (TARGETED)**: run only when diff touches auth, HTTP endpoints, DB writes, file paths, user input, credentials, permissions, or roles. Skip for style/docs/config-only diffs.
- `api-reviewer`
  Purpose: contract changes, integration compatibility, request/response semantics, and retries.
  **Trigger**: only when diff modifies API routes, response shapes, or shared types.
- `testing-reviewer`
  Purpose: deep test quality, missing coverage, fixture accuracy, and regression safety.
  **FULL only** — for INLINE/TARGETED, testing checks are embedded in software-reviewer.

### Surface Specialists (conditional — add when diff shape warrants)

- `performance-reviewer`
  When: hot paths, query-heavy code, N+1 patterns, heavy loops.
- `maintainability-reviewer`
  When: complexity balloons, coupling increases significantly.
- `data-migration-reviewer`
  When: schema changes, data migrations, backfill operations.

### Interaction Reviewers

- `caller-callee-reviewer`
  Purpose: verify changed code still matches direct callers, callees, adapters, and registration points.
- `shared-contract-reviewer`
  Purpose: verify shared types, API contracts, public interfaces, and fixtures remain compatible together.
- `state-flow-reviewer`
  Purpose: verify defaults, retries, error propagation, state transitions, and multi-step behavior remain coherent across files.

### Synthesis

- `synthesis-reviewer`
  Purpose: parent reviewer that merges surface and interaction outputs, resolves contradictions, and decides whether the system behavior still holds across boundaries.

### Final Passes

- `adversarial-reviewer`
  Purpose: find production failure modes and nasty edge cases the structured review and synthesis missed.
  Source bias: gstack-review adversarial posture.
  **FULL only** — skip for INLINE/TARGETED unless diff touches a shared public surface (routes, public API, shared types).

### Verification

- `false-positive-verifier`
  Purpose: read actual code in context and downgrade noise before reporting.

## Workflow

## Workflow Tier (judge before spawning any agents)

| Tier | Pick when | Agent policy |
|------|-----------|-------------|
| **INLINE** | Diff is ≤3 files, isolated module, no shared contracts, no security surface | Orchestrator reviews inline: read diff, grep callers, report findings. One false-positive-verifier at the end only. |
| **TARGETED** | 2–5 files, some shared types or API surface, no schema migration or auth change | software-reviewer always. security-reviewer only if diff touches auth/HTTP/DB/user-input. api-reviewer only if routes changed. testing-reviewer skipped (embedded in software-reviewer). Add one interaction reviewer when the diff crosses a real boundary. Run synthesis-reviewer when 2+ reviewer outputs must be merged. adversarial skipped. |
| **FULL** | Schema migrations, auth/permission logic, breaking API changes, cross-service contracts, security-critical surfaces | Full cycle: all core surface reviewers + applicable specialists + interaction reviewers + synthesis-reviewer + adversarial + false-positive-verifier. |

**Default when unsure: TARGETED, not FULL.** Running a swarm on a 2-file diff is completeness theatre, not rigour.

### Agent-spawn gate (apply before every sub-agent dispatch)

Before spawning a reviewer agent, answer: **"Is this concern genuinely beyond what I can assess by reading the diff directly?"**
- **YES** → spawn the specialist.
- **NO** → note the finding inline. Don't delegate it.

Specialist reviewers exist for genuine blind spots — not for delegation of obvious checks. Obvious null-check or style issues → inline. Novel auth flow or trust-boundary shift → specialist.

### Findings Reporting Discipline (apply before surfacing any finding to the user)

**Confidence gate**: only report a finding if you are **≥80% confident** it is a real issue in this specific codebase.

- **Skip**: stylistic preferences unless they violate project conventions recorded in `memory.md` or `AGENTS.md`
- **Skip**: issues in unchanged code unless they are Critical security issues directly triggered by the diff
- **Consolidate**: similar issues into one finding (e.g., "4 functions missing error handling" → one finding, not four)
- **Cite**: every finding must have a `file:line` reference. Findings without evidence are noise.
- **Downgrade**: if the false-positive-verifier cannot confirm the finding against the actual code, it gets dropped — not softened.

**Signal rule**: if adding a finding requires hedging ("this might be a problem if...", "potentially..."), it doesn't meet the bar. Either the pattern is in the diff and is wrong, or it isn't reported.

2. Define review scope: diff, files, module, or branch.
3. Launch surface reviewers **per tier** (see tier table below — not all reviewers run in all tiers):
   - **INLINE**: orchestrator reviews inline only. One false-positive-verifier at end.
   - **TARGETED**: spawn software-reviewer always. Add security/api/surface specialists conditionally per triggers in tier table. Skip testing-reviewer (embedded in software-reviewer).
   - **FULL**: spawn all core surface reviewers + applicable specialists.
   - **Spawn all surface reviewers with `model: "claude-sonnet-4.6"`** — thorough but not adversarial.
4. Add surface specialists when the diff shape warrants them. — **`model: "claude-sonnet-4.6"`**
4.5. Run `consequence-agent` when the diff modifies a public interface, shared type, API route,
   DI container, or cross-module contract.
    - **Spawn with `model: "gpt-5.4"`**
    - Skill: `~/.agents/skills/consequence/SKILL.md`
    - Purpose: surface what the diff breaks **outside the diff** — callers, consumers, test fixtures,
      contracts that will silently drift. This is distinct from adversarial (which finds bugs in
      the changed code itself).
    - Output feeds into the interaction and synthesis passes.
    - Skip for single-file isolated changes with no shared interface dependencies.
5. Launch interaction reviewers when the diff crosses file or module boundaries:
   - `caller-callee-reviewer` for direct integration points, registrations, adapters, and changed dependency edges
   - `shared-contract-reviewer` for routes, shared types, request/response shapes, public interfaces, or fixture compatibility
   - `state-flow-reviewer` when defaults, retries, state transitions, async error flow, or multi-step behavior changed
   - **Spawn interaction reviewers with `model: "claude-sonnet-4.6"`**
   - Each interaction reviewer receives: diff summary + relevant surface-review findings + consequence output when present
6. Run `synthesis-reviewer` as the parent reviewer whenever 2+ reviewer outputs must be merged.
   - **Spawn synthesis-reviewer with `model: "gpt-5.4"`**
   - It must:
     - merge surface and interaction findings
     - resolve contradictions between reviewers
     - identify emergent bugs that no single file reviewer proved alone
     - decide whether changed surfaces still behave correctly together
     - produce a deduplicated candidate findings list for the final passes
7. Run `adversarial-reviewer` as a separate pass for production-risk thinking.
   - **Spawn adversarial-reviewer with `model: "gpt-5.4"`** — cross-provider from Claude specialist reviewers. GPT's different training distribution catches blind spots Claude specialists share. See ensemble rule in copilot-instructions.md.
8. Run `false-positive-verifier` — **BLOCKING GATE** (`model: "claude-sonnet-4.6"`):
    - **No finding above Low severity may be reported to the user without verifier confirmation.**
    - The verifier must read the actual file + surrounding context for every Medium/High/Critical finding.
    - It must confirm or downgrade each finding with a direct `file:line` citation.
    - Downgrade if: the cited code does not match what the reviewer described, the finding was already fixed in the same diff, or the pattern is recorded as safe in `memory.md`.
    - Without a completed verifier pass, hold the full findings list — do not present it.
9. Report findings ordered by severity with file:line references.
10. If the user asks for fixes, apply them and re-run relevant checks.
11. Write back review memory:
    - **Session scratch first**: write running findings to `~/.agents/session-state/{session_id}/scratch.md` during the review. Promote only at step 11.
    - write full findings, attempted verifications, and next actions to `~/.agents/session-state/{session_id}/handoffs.md` (session-private body).
    - **Canonical registration + write routing**: follow `~/.agents/context/writeback-protocol.md`
    - **Workflow evidence**: follow `~/.agents/context/workflow-evidence-protocol.md` and record mode, repo context used, reviewers spawned/skipped, verifier steps, and write decisions.
    - For workflow learnings and reflection entry format, follow `~/.agents/context/reflection-protocol.md`
12. **Self-improvement pass (embedded reflect)** — run automatically after step 11:
    - follow `~/.agents/context/reflection-protocol.md`

## gstack Review Posture (applied throughout)

Apply gstack-review discipline at every stage:
- **Specialist decomposition**: assign each concern to the right reviewer, don't conflate them
- **Interaction discipline**: treat cross-file and cross-module behavior as a first-class review surface, not an afterthought
- **Parent synthesis**: do not let multiple reviewers report independently without one parent pass deciding whether the system behavior still hangs together
- **Adversarial challenge**: after structured review, attack: what would go wrong in production?
- **False-positive filtering**: read the actual code before reporting — don't report on assumptions
- **Production-risk framing**: for every High/Critical finding, describe the real-world failure mode
- **Severity discipline**: only escalate to Critical/High when the failure mode is concrete and evidenced

## Severity Guide

- **Critical** — data corruption, auth bypass, silent compatibility regression, schema corruption
- **High** — missing tests on behavior changes, boundary leakage, contract breakage, injection risk
- **Medium** — coupling increases, maintainability decay, missing edge case coverage
- **Low** — style drift in untouched code (report only if it blocks something)

## Layered Architecture Traps

These are recurring patterns in vibe-coded layered codebases (domain/application/infrastructure/api). Check for them explicitly during every review — they are easy to miss and expensive to fix later:

**DI bypass (P4)**: `new XxxService()` or `new XxxRepository()` inside application service constructors or route handlers → services self-wiring instead of receiving deps from a container. Ask: where does this class get its dependencies? If the answer is "it creates them itself", it's a P4 violation.

**Pass-through wrapper (P6)**: Infrastructure class method body is a single `return legacyModule.fn(params)` → class adds no value, real logic lives outside the layer. Ask: does this class contain any implementation, or is it purely delegation? If purely delegation, it's a wrapper anti-pattern.

**Schema re-declaration (P1)**: New interface or Zod schema declared inline, or in a layer file, when one already exists in the canonical schema package → schema drift between caller and receiver. Ask: is this type declared exactly once, in the right place?

**Silent fallback (P7)**: Evaluator/validator/quality-check returns a positive signal when the backing service is unavailable → quality gate bypass. The most dangerous pattern: `if (!config) return fallbackValue` on any path that is supposed to measure quality. Ask: what does this code return when the external dependency is down or misconfigured?

**Wiki staleness (P8)**: New public export, API endpoint, or service added without updating the project wiki/index → future agents and developers work from stale discovery context. Ask: is the export index updated?

## Rules

- Prioritize bugs, regressions, security issues, and missing tests.
- Do not suggest unrelated feature work.
- Do not spend review budget on style-only comments in untouched code.
- Be explicit about residual risk and testing gaps when no findings are confirmed.
- Check `memory.md` before escalating recurring issues — distinguish new findings from known/deferred.
- Use `handoffs.md` to continue unfinished reviews across sessions.
- Never rewrite workflow prompts in-place during a review run.
- Store self-improvement candidates in `reflections.md` for later consolidation.
- **Frontend blank-screen diagnosis**: check the browser DevTools console for JS errors FIRST before
  any source-code analysis. Source analysis cannot detect HMR runtime failures or React render crashes.
- **Context budget guard**: see global rule in `~/.agents/instructions.md`. When reading
  results from 3+ parallel agents, extract a ≤200-word summary per agent before reading the next.
  Never accumulate raw full outputs from 3+ large agents in the same response turn.

## Parallel-reviewers mode (opt-in)

Default review is sequential: surface → interactions → synthesis → adversarial → verifier.

When `swarm-classifier.ps1` returns `mode: swarm-review` (parallel-safe verb,
small scope), run the **review-only swarm** instead:

1. one sequential implementer (or take the existing diff)
2. fan out reviewers concurrently — one per lens:
   - security
   - performance
   - maintainability
   - data integrity / migrations
   - api contract
   - testing
3. one synthesizer merges findings (same as full swarm)
4. one false-positive verifier filters

This is the right default for polish-quality work on focused features.
Cheaper than full fan-out, more thorough than single-reviewer sequential.
See `~/.agents/skills/swarm/SKILL.md` for the full template.
