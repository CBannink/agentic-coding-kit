## Default Agent Matrix

### Explore
- `architecture-explorer`
  Purpose: map structure, boundaries, and moving parts.
- `surface-explorer`
  Purpose: inspect APIs, capabilities, interfaces, and dependencies.
- `impact-explorer` *(merges risk-explorer + ops-explorer)*
  Purpose: identify trust boundaries, safety concerns, failure modes, performance bottlenecks, operational concerns, and adoption impact. One agent covers both risk and ops — they read the same areas.

### Theorize
- `pragmatist`
  Purpose: recommend the lowest-risk workable path.
  Source bias: senior engineer execution realism.
- `skeptic`
  Purpose: challenge assumptions and expose weak reasoning.
  Source bias: gstack hard-nosed review style.
- `security-reliability` *(conditional — invoke only when topic explicitly covers auth, trust boundaries, data handling, or production risk)*
  Purpose: analyze trust boundaries, resilience, and production risk.
  Source bias: gstack review specialists.
- `product-wedge` *(conditional — invoke only for product direction, build-vs-buy, or status-quo replacement analysis)*
  Purpose: frame the user problem, wedge, and status-quo replacement when applicable.
  Source bias: gstack office-hours.

### Verify
- `claim-verifier`
  Purpose: verify disputed or important claims against code, docs, tests, or data.

## Workflow

## Workflow Tier (judge before spawning any agents)

| Tier | Pick when | Agent policy |
|------|-----------|-------------|
| **INLINE** | Question is narrow and answerable from 2–3 targeted reads. Design already understood. No real tradeoffs to surface. | Orchestrator does it inline: read, reason, answer. No sub-agents. |
| **TARGETED** | 2–4 independent angles needed, OR some uncertainty about design/tradeoffs, OR comparing ≤3 options | 2 explorers max (not 4). Pragmatist only — add skeptic only if real tradeoffs exist. Skip claim-verifier if evidence is direct (file:line). |
| **FULL** | Architecture readiness, design unknown, genuine multi-option tradeoffs with non-obvious blast radius, security/production-risk topic | Full cycle: 2–3 explorers + pragmatist + skeptic + claim-verifier + consequence-agent. |

**Default when unsure: TARGETED, not FULL.** Use FULL only when you genuinely cannot synthesise without multiple adversarial perspectives.

### Agent-spawn gate (apply before every sub-agent dispatch)

Before spawning any agent, answer: **"Can I answer this inline from what I already know or with ≤3 targeted reads?"**
- **YES** → do it inline. grep / view directly in this response.
- **NO** → spawn the agent, but only for the specific gap — not for the full standard roster.

**4 explorers is almost never necessary.** Most codebases require 1–2 targeted reads to understand a module. Spawn only when parallel exploration of genuinely independent areas saves time. Single-module questions → inline read, not an explorer.

---

1. Load repo-local context files (listed above) when they exist.
   - **Parallel instance guard**: scan `.codex/context/handoffs.md` for session-tagged entries from the last 60 min. Read only the tag line of each recent entry. If a recent entry has a different task slug than your current task → log "⚠️ PARALLEL INSTANCE on [{task}]" and treat shared files as append-only. If same task → resume from that entry. If no recent entries → load normally.
   - **memory.md filter**: use only entries that are repo-architectural facts. Entries that look like task progress from another instance are noise — ignore them.
   - **Session Handoff Index scan**: after loading memory.md, scan the `## Session Handoff Index` table. For each row: ask "does this session's summary overlap with what I'm analyzing?" If yes → read that handoff path before proceeding. If no → skip it entirely. Never auto-load all handoffs.
2. Explore with 2–3 parallel fact-finding agents. Gather facts only — no conclusions yet.
   - **Spawn explore agents with `model: "gpt-5.4-mini"`** — 0.33x cost, parallel tool-calling, codebase mapping.
   - **Max 3 explorers.** Most tasks need 1–2. Spawn only when parallel exploration of genuinely independent areas saves time. Single-module questions → inline read, not an explorer.
3. Synthesize findings into a shared evidence packet.
4. Theorize with at least 2 perspective agents arguing from different trade-offs.
   - Always include: `pragmatist` + `skeptic`
   - **Pragmatist: `model: "claude-sonnet-4.6"`** — execution realism from Claude's training.
   - **Skeptic: `model: "gpt-5.4"`** — cross-provider by design. GPT challenges Claude's pragmatist output with genuinely different priors. Disagreement between them is signal, not noise. See ensemble rule in copilot-instructions.md.
   - **Other theorize agents: `model: "gpt-5.4"`** — synthesis and arbitration.
   - Add `security-reliability` only when topic explicitly covers auth, trust boundaries, data handling, or production risk — not as a default for every analysis
   - Add `product-wedge` only for product direction, architecture selection, or build-vs-buy topics
4.3. **Claim-verifier pass** — **BLOCKING GATE** before synthesis:
   Run `claim-verifier` (`claude-sonnet-4.6`) on the combined theorize outputs.
   - For every factual claim made by pragmatist or skeptic that is disputable: verify it against code, docs, or direct evidence with a file:line citation.
   - Downgrade claims that cannot be verified: mark as "unverified assertion" in the evidence packet.
   - Do NOT let unverified claims enter the synthesis as confirmed facts.
   - Claims about tradeoffs and opinions are exempt — only factual claims about what code does, what tests cover, what APIs return, etc. need verification.
4.5. Run `consequence-agent` when the analysis involves a proposed change, design option comparison, or
   architectural decision that touches shared interfaces, public API surfaces, or cross-module contracts.
   - **Spawn with `model: "gpt-5.4"`** — multi-hop causal chains need premium reasoning.
   - Skill: `~/.agents/skills/consequence/SKILL.md`
   - In /analyze context: run one consequence-agent per option when comparing options — this projects
     the concrete blast radius of each choice and enables evidence-based comparison.
   - Output feeds into **synthesis (step 5)**, not back into theorize (which is already complete). The verified claims from step 4.3 are passed to the consequence-agent as input.
   - Skip for pure research tasks with no implementation options being evaluated.
5. Identify agreements, disagreements, and blind spots explicitly.
6. If the topic is root-cause analysis → use **gstack-investigate** discipline instead.
7. If the topic is architecture readiness → use **gstack-plan-eng-review** pressure.
8. If the topic is product direction → add `product-wedge` and use **gstack-office-hours** framing.
9. If blind spots are material, run targeted exploration and re-synthesize.
10. Verify testable claims against code, docs, or direct evidence.
10.5. **Build Brief owner-verification gate** — **BLOCKING** when the analysis will recommend an implementable fix:
    - For every file named in the recommendation or Build Brief, verify:
      - `OWNER VERIFIED`: the exact file:line/function that directly owns the broken behaviour
      - `FALSE OWNER RULED OUT`: at least one nearby plausible file (caller/callee/presenter/formatter) checked and explicitly ruled out
    - If the symptom is wrong user-visible output, inspect both the producing module and the presentation layer before naming the owner.
    - If the symptom is wrong derived data, inspect both the calculator/normalizer and the caller that surfaces it.
    - Do not let the Build Brief name a file based only on intuition, architectural taste, or “smallest diff” preference.
11. If stable repo facts confirmed → update `.codex/context/memory.md` when it exists.
    - **Write routing + numeric baselines**: follow `~/.agents/context/writeback-protocol.md`
    - **Workflow evidence**: follow `~/.agents/context/workflow-evidence-protocol.md` and record mode, repo context used, major agents spawned/skipped, evidence commands, and write decisions.
12. If next-session actions changed → write the full session body to `~/.agents/session-state/{session_id}/handoffs.md` FIRST.
    **Canonical registration**: follow `~/.agents/context/writeback-protocol.md`
    When a Build Brief is produced, it goes in the session-private file, not the shared file. Consume it from there only if the task slug matches.
    When the analysis concludes with an implementable recommendation, append a **Build Brief** section:

    ```
    ## Build Brief [YYYY-MM-DD]
    - Source: analyze
    - Decision: [what was decided]
    - Objective: [what /build should implement]
    - Affected files: [exact paths]
    - Ownership proof: [for each file: why it directly owns the defect or required change]
    - False owners ruled out: [nearby plausible files checked and why they are not the right fix target]
    - Known blast radius: [consequence-agent summary, or "not traced"]
    - Architectural constraints discovered: [list]
    - Modules already mapped — /build Phase 0 can skip: [list]
    - Next steps for /build: [ordered task list]
    ```

    Use today's date in YYYY-MM-DD format (system local date) as the section header. For backward compatibility, `/build` may also accept the legacy `## Analysis-to-Build Brief [YYYY-MM-DD]` header, but new sessions should write `## Build Brief [YYYY-MM-DD]`.
13. If analysis surfaced workflow gaps, false-positive patterns, or reviewer blind spots with concrete evidence
    → capture them using `~/.agents/context/reflection-protocol.md`.
14. **Self-improvement pass (embedded reflect)**: read `.codex/context/reflections.md` if it exists.
    If **5+** unaddressed entries, run consolidation using `~/.agents/context/reflection-protocol.md`.
    Repo-local targets: apply directly. Global targets (`~/.agents/skills/`, `copilot-instructions.md`): ask user first.

Before the final synthesis, include a compact **Workflow Evidence** block.

## Rules

- Never skip the explore phase for non-trivial analysis.
- Present disagreements instead of silently picking a winner.
- Keep facts separate from recommendations.
- Cite concrete evidence (file:line or doc section) in the final synthesis.
- Never write a Build Brief that names a file whose ownership has not been verified with file:line evidence.
- Write only durable repo-architectural facts to `memory.md` — no task progress, no session chatter. Apply the write gate: "Would this be useful to a completely different instance doing a completely different task in this repo?"
- Use `handoffs.md` for current status and next steps, always with a session tag. Skip entries whose task slug doesn't match your current task.
- Never claim a finding is confirmed without pointing at the actual evidence.
- **Frontend blank-screen diagnosis**: check the browser DevTools console for JS errors FIRST
  before any source-code or network analysis. Source analysis cannot detect HMR runtime failures,
  stale module graphs, or React render crashes — only the console can.
- **Context budget guard**: when reading results from 3+ parallel agents, extract a ≤200-word
  summary per agent before reading the next. Never accumulate raw outputs from 3+ agents in the
  same response turn. See the global context budget rule in `~/.agents/instructions.md`.
