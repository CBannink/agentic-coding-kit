## Default Agent Matrix

### Phase 0: Freshness / Delta Validation

- `plan-freshness-checker`
  Purpose: confirm the approved `plan.md` still matches the task and repo state; trigger re-planning only on material drift.
- `delta-explorer`
  Purpose: inspect only the specific gaps or repo drift not already covered by the approved plan.
- `patterns-explorer`
  Purpose: only when implementation patterns remain unclear after reading the approved plan; otherwise skip.

### Phase 1: Plan

- `eng-plan-reviewer`
  Purpose: fallback only — challenge architecture, data flow, failure modes, and test gaps when `/plan` did not already do so or the plan became stale.
  Source bias: gstack plan-eng-review.

### Phase 2-6: Build Loop (max 5 iterations)

- `implementer`
  Purpose: implement only the scoped task with minimal diff and fresh context.
  Source bias: Superpowers subagent-driven-development.
- `spec-reviewer`
  Purpose: verify the implementation matches the agreed plan and did not add scope.
- `code-quality-reviewer`
  Purpose: check maintainability, correctness, conventions, test quality, and observability. For the FULL step-9 deep pass, extend to: are all new behaviours specifically tested by name? Are mocks accurate? Are fixtures updated? Are error/edge cases covered? Are errors logged with context (not swallowed)? Is trace context forwarded?
- `modularity-expert`
  Purpose: run an anti-slop architecture-integrity pass. Check reuse-first discipline, new-file justification, module placement, duplicate helpers/types/classes, speculative abstractions, and pass-through wrapper files.
  Source bias: `~/.agents/skills/experts/modularity/SKILL.md`
- `security-reviewer`
  Purpose: review trust boundaries, injection risks, auth mistakes, data leaks, and failure handling.
  Source bias: gstack review specialists.
- `build-loop-gate` — **BLOCKING GATE**
  Purpose: (1) for each finding from code-quality, modularity, or security, read the actual file+context and verify it has a real file:line citation — downgrade theoretical or already-fixed findings; (2) based on verified findings + test output, confirm pass/fail and report only confirmed blocking issues. Merges `false-positive-verifier` + `verification-gate` into a single agent.
  Model: `(balanced model)`

### Phase 7: Final Validation

- `error-handling-adviser` *(skip when: diff contains no async calls, no external data sources, no null-returning APIs, and no new error paths — e.g. pure math, config-only, style-only changes)*
  Purpose: check that all new error paths are handled explicitly.
  Ask: missing try/catch on async calls? unhandled promise rejections? missing null checks on API/external responses? type narrowing holes? silent catch-and-swallow patterns?
  Model: `(balanced model)`

- `performance-adviser` *(invoke when diff touches DB queries, React lists/maps, hot loops, or API handlers)*
  Purpose: judge code quality from a performance angle.
  Ask: N+1 query patterns? React re-renders missing memoization? synchronous I/O in hot paths? missing pagination on large result sets? unnecessary computation inside render or tight loops?
  Source: `~/.agents/skills/experts/performance/SKILL.md`
  Model: `(premium reasoning model)` (cross-provider — different training catches different perf anti-patterns)

- `qa-reviewer`
  Purpose: browser or user-flow validation for UI/web changes, including UI-to-backend default parity and artifact-rendering safety.
  Source bias: gstack-qa.

- `ui-ux-expert` *(invoke when diff introduces or changes any user-visible flow, component, onboarding step, error state, navigation, or information hierarchy — not limited to .tsx files)*
  Purpose: UX flow + component structure **code review** (props, boundaries, Tailwind consistency). Does NOT use screenshots — use the visual gate below for that.
  Source: `~/.agents/skills/experts/ui-ux/SKILL.md`
  Models: a premium reasoning model (UX/design critique — Gemini unavailable in CLI) + Claude Sonnet 4.6 (UI implementation review)

- `visual-gate` *(invoke when `frontend-detector.ps1` returns `visual_loop_recommended=true`)*
  Purpose: screenshot-based design review with UX→UI agent split. Distinct from `ui-ux-expert` (code review) — this is **pixel review**.
  Sequence:
  1. `pwsh ~/.agents/tools/dev-server-runner.ps1 -RepoRoot .` — auto-start dev server
  2. For any new screen in the diff that's not in `.agents/screen-flows.yaml`: spawn `playwright-navigator` to emit the YAML block
  3. `pwsh ~/.agents/tools/playwright-runner.ps1` — capture before/after shots
  4. `ux-driver` — structural critique (hierarchy, flow, density, a11y); blocks if `structure_ok=false`
  5. `ui-driver` — visual critique (typography, color, spacing, slop), only if UX passed
  6. `pwsh ~/.agents/tools/visual-diff.ps1` — confirm changes were intentional, no regressions elsewhere
  7. Stop dev server when done
  Source: `~/.agents/skills/ux-driver/SKILL.md` + `~/.agents/skills/ui-driver/SKILL.md` + `~/.agents/skills/playwright-navigator/SKILL.md`
  References: `~/.agents/context/design-references.md` (read by ux-driver and ui-driver)

- `adversarial-reviewer`
  Purpose: attack the diff for production failure modes, regressions, and hidden risks. In the prompt include: "Also check observability: are errors logged with context (not swallowed)? Is trace context forwarded across service boundaries? Are key user actions logged?"
  Source bias: gstack-review adversarial posture.

- `final-verifier` — **BLOCKING GATE**
  Purpose: (1) verify that expert findings have file:line evidence and actually apply to this codebase's specific context — downgrade theoretical findings not present in the code; (2) enforce no-completion-claims-without-fresh-evidence (Iron Law). For INLINE/TARGETED: run as a single merged pass. For FULL: run as two distinct passes (expert findings first, then completion evidence).
  Model: `(balanced model)`
  Source bias: Superpowers verification-before-completion.

## Workflow

**Step 0a — Wiki context pre-flight** (BEFORE any reviewer / explorer / implementer spawn — load-bearing):

If `.wiki/` exists, run `wiki-resolver.ps1` FIRST and embed the returned `prompt_block` in EVERY downstream subagent prompt:

```powershell
pwsh ~/.agents/tools/wiki-resolver.ps1 -Task "{task slug}" -ChangedFiles "{comma-sep diff list}" -RepoRoot .
```

The resolver returns `index.md` (always) plus matched sections (changed-file overlap or task-name match). Pass its `prompt_block` field verbatim into each implementer / reviewer prompt. **Never** bulk-read `.wiki/sections/`. **Never** spawn a subagent without first checking the resolver — even if you think the task doesn't touch the wiki.

If `.wiki/` is missing, surface the warning from `pre-session.ps1` and recommend the user run `/wiki-init` before non-trivial work. Continue without wiki context only if the user opts in explicitly.

**Step 0b — Scope Classification** (always, before anything else — machine-enforced):

Run the scope classifier script to get an objective scope reading:
```powershell
pwsh ~/.agents/tools/scope-classifier.ps1
```
The script reads `git diff --name-only HEAD` and outputs `{ scope, reason, file_count, files }`. Use its output as the authoritative scope. **Override upward only** (never downward) if you have concrete evidence the classifier missed something.

Then initialize the session state file:
```powershell
pwsh ~/.agents/tools/state-init.ps1 -SessionId "{session_id}" -Task "{brief-task-slug}" -Scope "{ISOLATED|SHARED|CRITICAL}" -ScopeReason "{classifier reason}"
pwsh ~/.agents/tools/workflow-evidence.ps1 -SessionId "{session_id}" -Mode "build" -Scope "{ISOLATED|SHARED|CRITICAL}" -ScopeReason "{classifier reason}"
```

| Class | Criteria | Required phases | Optional/skip |
|-------|----------|-----------------|---------------|
| **ISOLATED** | Isolated to 1 module/package, no shared types/routes/schema, ≤5 files estimated, no auth/DI/cross-module impact | Steps 1–4, 7–11 | Skip: delta exploration unless freshness fails (step 5), fallback plan pressure (step 6), adversarial-reviewer |
| **SHARED** | Touches 2+ modules, or shared interfaces/types/routes, or new service wiring | All steps | All agents per their trigger conditions |
| **CRITICAL** | New architecture, auth/permission changes, schema migrations, public API changes, breaking changes | All steps + extra adversarial pressure | None — run everything |

**When unsure: classify upward.** A ISOLATED misclassified as SHARED wastes tokens. A CRITICAL misclassified as ISOLATED ships a bug.

## Workflow Tier (judge this before spawning any agents)

After scope classification, the orchestrator picks a workflow tier. Scope is an input — not a 1:1 mapping. Use judgment.

| Tier | Pick when | Agent policy | Max sub-agents |
|------|-----------|-------------|----------------|
| **INLINE** | ≤3 files, single module, design fully understood, no shared types/contracts | No sub-agents. Act inline with view/grep/edit. Inline verification only — no final-verifier agent. | **0** |
| **TARGETED** | 2–5 files across modules, OR shared types but design is clear, OR fresh Analysis-to-Build Brief from today, OR an approved same-session `/plan` artifact exists | Skip broad Phase 0 if brief/plan covers it. Mechanical changes inline — no implementer agent. Sub-agents only for novel/complex logic. No separate test-quality or observability agents (embedded in code-quality-reviewer). | **6** |
| **FULL** | New architecture, schema migrations, security-critical paths, design unknown going in, OR ≥5 files with novel logic in each | All phases. All agents per their trigger conditions. Code-quality-reviewer runs a dedicated deep test-quality + observability pass in step 9. Track running total — if >12 agents spawned, pause and surface to user. | **12** |

**Default when unsure: TARGETED, not FULL.** FULL is for genuine unknowns — not for comfort or completeness theatre.

### Agent-spawn gate (apply before every sub-agent dispatch)

Before spawning any sub-agent, answer: **"Can I do this inline in ≤5 tool calls?"**
- **YES** → do it inline. view / grep / edit / powershell directly. No agent.
- **NO** → spawn the agent.

A sub-agent costs 5–20× more tokens than inline work. Spawn only when the task requires:
- Reasoning you cannot complete in a single response turn
- Reading + synthesising 3+ files simultaneously with non-trivial logic
- Genuinely cross-provider adversarial perspective
- Implementation spanning ≥3 files with novel logic in each

**Mechanical work is never a valid reason to spawn.** Field renames, import updates, model mirroring, simple wiring — these are always inline.

When you skip an agent that the tier table might otherwise suggest, record the skip:

```powershell
pwsh ~/.agents/tools/workflow-evidence.ps1 -SessionId "{session_id}" -AddSkippedAgent "{name}|{reason}"
```

When you skip a major workflow mode or collapse it into an inline step, record that too:

```powershell
pwsh ~/.agents/tools/workflow-evidence.ps1 -SessionId "{session_id}" -AddModeDecision "/review skipped|INLINE diff was two-line mechanical fix; inline review performed instead"
```

## Superpowers Principles Applied

**verification-before-completion:**
- No completion claims without running verification commands and reading the output.
- No "should work", "probably passes", "looks correct" without evidence.
- Run the full command fresh. Read exit code and output. Then claim the result.

**subagent-driven-development:**
- Fresh isolated sub-agent per task = clean context.
- Two-stage review after each task: spec compliance first, then code quality.
- Never skip reviews. Never accept "close enough" on spec compliance.

**systematic-debugging:**
- State symptom precisely.
- List competing hypotheses ordered by likelihood.
- Design the cheapest test that distinguishes between them.
- Eliminate with evidence. Fix only after root cause confirmed.

## Build Loop Rules

- **File-read gate**: before an implementer edits a file for the first time in this session, it must have explicitly read that file. Include in every implementer prompt: "Read [file] before editing it." Editing without reading first is the primary cause of context-mismatch bugs.
- **Recovery gate**: same error 2+ consecutive times → invoke agent-recovery before next attempt. Never retry blindly.
- Always explore before coding.
- For non-trivial features, design and plan before implementation.
- **Anti-slop gate**: any new file, helper, class, schema, or abstraction must earn its existence. Reuse existing code first. If something new is added, the builder or modularity-expert must be able to justify why reuse was insufficient, why the placement is correct, and why the abstraction is not just scaffolding noise.
- Always verify before claiming done.
- Cite file references when summarizing findings.
- Stop and ask the user after 3 failed root-cause attempts or 5 full build-loop failures.
- Do not add features beyond scope.
- Prefer existing project dependencies and conventions over introducing new ones.
- `handoffs.md` is operational memory, not a design doc.
- `memory.md` is durable repo memory — max 40 entries. Remove superseded entries when adding new ones. Never annotate superseded entries — delete them.
- `reflections.md` is for suggested workflow improvements. Promoted entries are **deleted** (not annotated). Only unaddressed entries remain. 5+ unaddressed = mandatory /reflect before starting.
- `handoffs.md` rolling window: on session start, entries older than 2 sessions go to `handoffs-archive.md` or are deleted. Never load stale multi-session history.
- **Subagent context isolation**: pass each subagent only what it needs. Implementers get task + patterns + integration points. Reviewers get the diff + their specific concern area. Nobody gets the full memory.md/handoffs.md unless they explicitly need durable architecture facts. Extract the relevant slice and embed it in the prompt.
- **Role-memory gate**: if `.kit/context/agent-memory/shared.md` exists, pass only the relevant excerpt. If `.kit/context/agent-memory/{role}.md` exists, pass it only to the matching role. Do not spray specialist memory to unrelated agents.
- **Mechanical role-memory gate**: before spawning any implementer or specialist reviewer, run `specialist-memory-resolver.ps1` for that exact role. If it returns `found=true`, inject the returned `prompt_block`. Do not hand-roll role-memory loading from memory files in the orchestrator.
- **Read-stop gate (enforced)**: after explore synthesis, the orchestrator stops reading source files. File reads the implementer needs are embedded as instructions in its prompt, not done inline by the orchestrator. If you have done 3+ file reads post-synthesis, stop — you are in excavation mode, not orchestration mode. Redirect those reads to the implementer.
- **Plan-first execution rule**: when an approved same-session `/plan` artifact exists, `/build` should prefer executing against it over reopening broad exploration. Re-explore only on freshness failure or a specific missing fact.
- **Plan-to-diff gate**: the changed-file set must still match the approved plan. If implementation adds an unplanned file, new abstraction, or moved module, either update the plan explicitly first or treat it as scope drift and have `spec-reviewer` + `modularity-expert` challenge it.
- **Plan artifact gate**: for non-trivial builds, `~/.agents/session-state/{session_id}/plan.md` must exist before implementation begins. If the task changed materially after approval, refresh the plan and re-approve instead of silently drifting.
- **Run-packet gate**: keep `run-packet.json` current enough that a compaction or resume path can recover the execution contract without rereading the entire planning/build transcript.
- **`.wiki` update**: if `.wiki/features.md` exists in the repo, update it (and `.wiki/.features`) when the build adds or changes a user-visible capability.
- **UI default-contract gate**: if the build adds a UI over an existing CLI/script/API flow, verify the UI's default selections and option enums match the underlying contract. Prefer a shared source of truth; otherwise add an explicit contract check or test.
- **Artifact-contract gate**: if the build reads historical/generated artifacts (run folders, manifests, JSON results, logs), validate parsing against real representative samples from the repo or captured fixtures rather than only happy-path synthetic data.
- **Unsafe-markup gate**: any value derived from artifacts, run metadata, logs, labels, or user-configurable text must render as plain text by default. Do not use raw `innerHTML` unless the content is trusted and explicitly sanitized.
- **Agent tracking**: for each sub-agent spawned, run `pwsh ~/.agents/tools/state-gate.ps1 -SessionId "{SESSION_ID}" -AddAgent "{name}" -EnforceAgentCap`. This updates `state.json` and hard-blocks when the tier cap is exceeded.
- **Workflow evidence**: for each spawned sub-agent, also run `pwsh ~/.agents/tools/workflow-evidence.ps1 -SessionId "{SESSION_ID}" -AddAgent "{name}|{reason}"`.
- **Verification evidence**: after each build/test/lint/types/security command used for completion evidence, record it with `pwsh ~/.agents/tools/workflow-evidence.ps1 -SessionId "{SESSION_ID}" -AddVerification "{command}"`.
- **Write-decision evidence**: before completion, record explicit no-op or write decisions for repo memory/history/wiki.
- **INLINE review evidence**: when no separate reviewer is spawned, record what the inline review actually checked with `-AddReviewCheck`.

## Layered Architecture Compliance Gates

When building in a layered codebase (domain / application / infrastructure / api), check these at the END of every implementation before claiming done. These are the most common vibe-code architecture violations:

**Schema SST (P1)**: New types/schemas go in the canonical schema location (e.g., `packages/types`). Never re-declare a Zod schema or interface that already exists there. Use `z.infer<typeof xxxSchema>` for derived types — never hand-type a duplicate interface.

**DI container (P4)**: New services receive their dependencies via constructor params. Zero `new Repository()` or `new Service()` calls inside application services, infrastructure classes, or route handlers. All instantiation happens in exactly one place (the container / bootstrap).

**Typed error hierarchy (P5)**: New error handling throws a typed error class (e.g., `NotFoundError`, `ValidationError`) that maps to HTTP status automatically via a `createHandler` wrapper. No inline `res.status(N).json({error})` scattered across handlers.

**Real infrastructure classes (P6)**: New infrastructure classes contain the actual implementation — not a 1-line delegation to a root-level module function. If the class body is only `return legacyModule.fn(params)`, it is a pass-through wrapper anti-pattern.

**No silent fallbacks (P7)**: Any evaluator, validator, or quality-check path must throw a hard error when the backing service is unavailable or unconfigured. Never return a positive/passing signal from a fallback. `if (!config) return defaultValue` on a quality check = banned pattern.

**Wiki-first (P8)**: After adding any new public export, service, or API endpoint — update the project's wiki/export index. One row per new export. Never leave discovery docs stale.

## Anti-Slop / Architecture-Integrity Gates

Apply these alongside P1-P8 whenever the build adds or reshapes code structure:

**Reuse-first proof**: before adding a new helper, class, type, schema, or hook, check for an existing reusable candidate. If you create a new one anyway, justify why reuse or extension was not correct.

**New-file justification**: every new file must have a clear reason to exist and belong in its chosen directory. "Keeps things tidy" is not enough. Random one-off files are a build smell.

**No duplicate abstractions**: near-duplicate helpers, schemas, wrapper classes, and mini-utilities are slop even when tests pass. Prefer extending or consolidating existing code.

**No pass-through scaffolding**: a new file or class whose body only forwards to another function/class without adding real behavior, boundary handling, or contract adaptation is a slop pattern. Delete it or fold it into the real owner.

**Plan fidelity**: implementation should follow the explored plan. Unplanned file creation, surprise module moves, or speculative abstractions require explicit justification and review, not silent acceptance.
